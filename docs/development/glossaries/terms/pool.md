# Pool

- Bounded context: swallow-wide. `api-server`, `dashboard`, and `cli` use this term with the same meaning.
- Definition: A swallow-owned, Site-scoped logical grouping of Servers used to partition resources for allocation and organization — a *resource pool* — that swallow defines and manages as desired state rather than merely observes. swallow's catalog controller makes every provisioner of the Site that supports an equivalent grouping (a MAAS *resource pool*) hold each Pool as specified, including a provisioner added later; when a provisioner has no such capability, swallow still owns the Pool and reports `capability_missing` for that provisioner.
- Allowed meaning: A managed resource identified by an opaque, stable swallow-issued `poolId`, with a `siteId`, a `generation`, and a spec of a `name` unique within its Site and an optional `description`; its status reports its realization on each provisioner of the Site. A Server is placed in at most one Pool through its own spec (`spec.poolId`, null for the provisioner's default resource pool); the Server Controller moves the machine and the effect appears on the Server's observed resource pool. A change made in the provisioner (a Pool removed, renamed, or redescribed, or a machine moved) is Drift and is reverted at the periodic resync. A resource pool that exists only in the provisioner is adopted into the catalog when first seen; the provisioner's default resource pool (MAAS `default`) is never part of the catalog. Deleting a Pool removes it from the provisioners first and is refused while a Server is placed in it. "Pool" always means this swallow-owned resource pool concept; the phrase "available pool" in Release refers to the provider returning a Machine to its ready state and is not this term.
- Disallowed meaning: Not a Zone (a Zone groups for availability/fault/organization; a Pool partitions resources for allocation), not a Site, not a Kubernetes/Slurm Platform, not a provider's "available pool" of ready Machines used when releasing, and not the provisioner's opaque resource-pool label carried through untouched — that earlier opaque pass-through is superseded by this swallow-owned model.
- Synonyms: Resource Pool. (A MAAS "resource pool" is the provider realization of a Pool.)
- Deprecated terms: None.
- Examples: "Create a Pool `research` in the lab Site; MAAS gains a matching resource pool." / "Move `gpu-node-01` from Pool `default` to Pool `research`; the provisioner records the machine's pool and reconcile mirrors it onto the Server." / "'Release returns a Machine to the provider's available pool' does not refer to a Pool."
- Related terms: Zone, Site, Server, Controller, Condition, Drift, Integration, OS Provisioning Provider, Machine, Release.
- Change note: Added 2026-09-14 to make Pool (resource pool) a swallow-owned, Site-scoped managed concept surfaced under the dashboard *Infrastructure* area, with optional provider realization. Disambiguated from the pre-existing informal use of "available pool" in the Release term. See decision 029. On 2026-10-31 ([decision 071](../../../decisions/071-provisioner-realized-desired-state.md)) the Pool catalog and Server placement became desired state realized by controllers: writes no longer wait for the provisioner, a placement can be cleared, and the catalog no longer drifts from the provisioner.
