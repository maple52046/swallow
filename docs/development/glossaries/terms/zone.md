# Zone

- Bounded context: swallow-wide. `api-server`, `dashboard`, and `cli` use this term with the same meaning.
- Definition: A swallow-owned, Site-scoped logical grouping of Servers — an availability, fault, or organizational grouping — that swallow defines and manages as desired state rather than merely observes. swallow's catalog controller makes every provisioner of the Site that supports an equivalent grouping (a MAAS *physical zone*) hold each Zone as specified, including a provisioner added later; when a provisioner has no such capability, swallow still owns the Zone and reports `capability_missing` for that provisioner.
- Allowed meaning: A managed resource identified by an opaque, stable swallow-issued `zoneId`, with a `siteId`, a `generation`, and a spec of a `name` unique within its Site and an optional `description`; its status reports its realization on each provisioner of the Site. A Server is placed in at most one Zone through its own spec (`spec.zoneId`, null for the provisioner's default physical zone); the Server Controller moves the machine and the effect appears on the Server's observed physical zone. A change made in the provisioner (a Zone removed, renamed, or redescribed, or a machine moved) is Drift and is reverted at the periodic resync. A physical zone that exists only in the provisioner is adopted into the catalog when first seen; the provisioner's default physical zone (MAAS `default`) is never part of the catalog. Deleting a Zone removes it from the provisioners first and is refused while a Server is placed in it.
- Disallowed meaning: Not a Site (a Zone lives inside one Site; a Site is a location, a Zone is a grouping inside it), not a Pool (a Pool partitions resources for allocation; a Zone groups for availability/fault/organization), not a Kubernetes/Slurm Platform, not a physical-placement hierarchy level (datacenter/room/rack), and not the provisioner's opaque zone label carried through untouched — that earlier opaque pass-through is superseded by this swallow-owned model.
- Synonyms: None. (A MAAS "physical zone" is the provider realization of a Zone, not a separate term.)
- Deprecated terms: None.
- Examples: "Create a Zone `rack-a` in the lab Site; MAAS gains a matching physical zone because its provisioner is grouping-capable." / "Place `gpu-node-01` in Zone `rack-a`; the Server controller moves the machine in MAAS, and the Server reports `realized` once it is there." / "A Site backed by a provisioner without zones still lists its swallow Zones."
- Related terms: Pool, Site, Server, Controller, Condition, Drift, Integration, OS Provisioning Provider, Machine.
- Change note: Added 2026-09-14 to make Zone a swallow-owned, Site-scoped managed concept surfaced under the dashboard *Infrastructure* area, with optional provider realization. This supersedes the note on the `provisioning` `Machine` that a provisioner's zone label is "carried through opaquely and not mapped onto any swallow hierarchy". See decision 029. On 2026-10-31 ([decision 071](../../../decisions/071-provisioner-realized-desired-state.md)) the Zone catalog and Server placement became desired state realized by controllers: writes no longer wait for the provisioner, a placement can be cleared, and the catalog no longer drifts from the provisioner.
