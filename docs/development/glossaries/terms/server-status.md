# Server Status

- Bounded context: swallow-wide, authoritative for `api-server`, `dashboard`, and `cli`.
- Definition: A server has **no single status**. Its condition is **three independent axes**, each owned by a different external system and each carrying its own `observedAt`. The `provisioning` and `membership` axes are absent until their owner has been observed at least once; the `health` axis is always classified when a Server is read, by swallow's monitoring policy (see below).
- Allowed meaning: The three axes are:

  | Axis | Owner | Answers |
  | --- | --- | --- |
  | `provisioning` | Provisioner (MAAS) | Can it be deployed, is a deployment running, did it fail; also power, ephemerality, lock, and the provider's last hardware inspection and test results |
  | `membership` | Kubernetes API, Slurm | Is it in a platform, in what role, is it draining |
  | `health` | The Site Prometheus (the Server's Node Exporter), within swallow's monitoring policy | Does swallow monitor it, and if so, is it up |

  An axis that has never been observed is **absent, not defaulted**: "we do not know" must never be presentable as "we know it is bad". A provisioner being unreachable does not make its servers unhealthy, and a server with no metrics is not down — it may simply not be scraped yet. The normalized `provisioning.state` is the value to branch on; its swallow-defined value set (`new | inspecting | ready | allocated | deploying | deployed | releasing | testing | rescue | broken | failed | retired | unknown`) is the OS Provisioning State term, and the provider's own label is display-only. `broken` and `failed` are distinct and must stay distinguishable at a glance: `broken` is a provider-marked unusable Machine (recoverable with Mark fixed), while `failed` is a last-lifecycle failure such as a failed deployment (recoverable with Recover or Release; see Provider Recovery). `rescue` is a diagnostic environment, not a recovery result (see Rescue Mode). `allocated` (reserved but not deployed — for example a deployment that never completed, or a verification borrow that ended early) is also a Recover/Release source, not a dead end, and must never be presented through a stale `deployed`-looking deployment result.

  The `health` axis is the exception to "absent until observed". It is a **classification by swallow's monitoring policy**, not an observation with a default, and it has four values:

  | `health.state` | Meaning |
  | --- | --- |
  | `up` | swallow lists a Node Exporter scrape target for the Server, and the Site Prometheus's latest scrape of it succeeded. |
  | `down` | swallow lists a Node Exporter scrape target for the Server, and the Site Prometheus's latest scrape of it failed. |
  | `unknown` | swallow monitors the Server but has no answer: it lists a target with no sample yet, at a Site without a Prometheus, or whose metrics read failed; or the Node Exporter policy covers the Server (present, `deployed`, not locked, Site automation enabled) but it has no target yet, for example an imported Server whose Node Exporter is not installed. A warning. |
  | `not_applicable` | swallow does not monitor the Server: it is neither a target nor covered by the policy, for example `ready`, `releasing`, absent, locked, or at a Site whose automation is off. Neutral. |

  Why classify instead of leaving the axis absent: whether swallow monitors a Server is a fact swallow owns (its scrape targets and its Node Exporter policy), not something it waits to observe. With only "absent", a Server swallow expects to monitor and is missing an answer for looks exactly like a Server swallow never meant to monitor, and only the first deserves attention. The classification still never presents "we do not know" as "we know it is bad": `down` requires a target whose scrape failed, `unknown` and `not_applicable` are never failures, and `observedAt` is set only for `up` and `down`, the values a sample stands behind. Only the Node Exporter decides health; GPU and other exporters do not.
- Disallowed meaning: A single collapsed value. Collapsing the three axes into one badge is disallowed: a server that is `deployed`, in no platform, and reporting no metrics is either a spare awaiting allocation or a broken host, and no rule can tell which. Do not use one axis to express another — provisioning state is not power state, membership is not health. Do not read `unknown` or `not_applicable` health as down, nor `not_applicable` as healthy.
- Synonyms: None. "Health" refers specifically to the `health` axis, not to the whole of a server's condition. The Dashboard labels the health values Up, Down, Unknown, and N/A; the domain values are `up`, `down`, `unknown`, and `not_applicable`.
- Deprecated terms: The closed six-value set `live | warning | error | maintain | offline | unknown` — a single operational status — is **superseded**. It predates the refoundation and never matched what the backend implements; the three axes replace it. A UI may still summarise the axes for a glance, but must not persist or filter on a single combined status.
- Examples: "A newly reconciled server has a `provisioning` axis but null `membership`, and its health is `not_applicable` until it is deployed and covered by the Node Exporter policy." / "An imported `deployed` Server whose Node Exporter is not installed yet reads health `unknown`, not `down`." / "Right after swallow releases a Server its health is `not_applicable`, even while the Site Prometheus still holds its last series." / "Filter the server list by `provisioningState=deployed`; there is no single `status` filter."
- Related terms: Server（the entity these axes describe）, OS Provisioning State（the value set of `provisioning.state`）, Server Lock（a provider-owned protection fact carried by the provisioning axis）, Software Assignment（the Node Exporter's assignment decides whether a Server is a health target）, Alert（a different concept, read from Alertmanager）.
- Change note: Rewritten from the previous single closed six-value set to the three-axis model of [decision 002](../../../decisions/002-server-identity.md) (server identity) and [decision 003](../../../decisions/003-metrics-label-contract.md) (metrics label contract), which is what `api-server`, `dashboard`, and `cli` implement. Updated 2026-10-04 ([decision 048](../../../decisions/048-os-provisioning-generic-states.md) (os provisioning generic states)): the `provisioning.state` value set moved to the OS Provisioning State term and the MAAS value `commissioning` became `inspecting`. Updated 2026-11-04: the `health` axis gained `unknown` and `not_applicable` and became always classified when a Server is read, by the Node Exporter scrape target and the Node Exporter policy; before, a Server without an answer had a null axis, which could not tell a Server swallow expects to monitor from one it does not, and a released Server read `down` from its stale series.
