# Local Repository

- Bounded context: Local Repository. `api-server` and `dashboard` use this term with the same meaning.
- Definition: A Site's own source of the artifacts a swallow deployment installs — OS packages, container images, Python packages, and files — kept by a Provider Adapter next to the control plane. When the Site chooses it, its Servers fetch every such artifact from it, so deployments do not reach the Internet; otherwise they fetch each from the upstream its module declares.
- Allowed meaning: One per Site, registered as the Site's Integration of kind `repository` (provider kind `pulp`, Pulp 3 today), which every installation registers: its endpoint is where swallow calls the provider's API, its `contentOrigin` setting is where Servers read content, and its write-only credential is the provider's admin password. swallow owns what it must contain — the `artifacts` the compiled modules declare in their `module.json`, together with the Site's user Repository Sources (a spec with a `generation`; the Ubuntu archive `ubuntu` is one) — and how the Site's deployments use it, the spec's Local Repository Mode (`upstream` until a user changes it, `cache`, or `offline`). While the mode is `cache` or `offline`, a controller in the worker converges that content into the provider and records the observed state of each source, file, and declared image; while it is `upstream`, the controller leaves the provider and what it holds alone. The artifacts themselves stay in the provider. The Local Repository is `ready` when deployments that fetch artifacts are accepted under its mode: never in `upstream` (they fetch from the upstreams); in `cache` when the Site's `repository` Integration is enabled, the controller has observed it and its last pass was not stopped by the Integration or its provider, and the addresses Servers read it at are known; in `offline` when, beyond that, every Repository Source is served, and every declared file and declared image is `ready` (an image once the provider stores every layer of it, so no Server pull reaches the upstream). Its content has one of these formats, the core's only words for them:

  | Format | What it holds |
  | --- | --- |
  | `deb` | Debian and Ubuntu packages from declared sources, synchronized on demand and signed with the Site's own key. |
  | `rpm` | RPM packages from declared sources; designed in, not yet realized. |
  | `oci` | Container images, through one pull-through cache per registry host. |
  | `python` | Python packages, through a pull-through cache of PyPI. |
  | `file` | Single files, each downloaded once and verified against its declared sha256. |

  A playbook flagged `fetchesArtifacts` receives, as the trusted variable `swallow_artifacts`, where each artifact comes from, decided when its Workflow is accepted: the declared upstreams in `upstream` mode, the Local Repository's addresses in `offline` mode, and in `cache` mode the Local Repository's address for what it serves and the declared upstream for the rest. A deployment that runs one is refused at acceptance while the Local Repository is not ready, unless the mode is `upstream`.
- Disallowed meaning: Not the Provisioner HTTP Proxy, which only forwards a provisioner's package traffic and pins nothing. Not where OS Images live (the provisioner keeps them), not a store of swallow's own data, and not a registry users push images to. Not "Pulp": Pulp is its current Provider Adapter, and `pulp`, `apt`, and `dnf` never appear in the core. Not a silent fallback: an `offline` Site never fetches from the upstreams while it is not ready, an `upstream` Site never fetches from it, and a `cache` Site fetches an artifact from its upstream only because the user chose that mode, recorded in each run.
- Synonyms: Local repo (informal).
- Deprecated terms: Artifact Repository (the planning name of its Provider Interface).
- Examples: "The Kubernetes deployment downloads the k0s binary from the Local Repository's files and verifies its declared sha256, instead of from GitHub." / "A Site whose Local Repository is `offline` cannot deploy a Kubernetes Platform while the Ubuntu archive is synchronizing for the first time: the request is refused with 409, naming the source to wait for." / "A newly installed Site does not use its Local Repository yet (`upstream`), so its first deployment downloads the k0s binary from GitHub and verifies the same sha256."
- Related terms: Local Repository Mode, Repository Source, Integration, Site, Provider Interface, Provider Adapter, Module Manifest, Controller, Desired State, Observed State, Provisioner HTTP Proxy.
- Change note: Added 2026-11-06 for [decision 078](../../../decisions/078-local-repository.md) (local repository): every role fetched its artifacts from the Internet, so deployment time grew with the number of Servers and the outbound bandwidth, offline Sites could not deploy, and nothing was pinned at the Site. The plan called its Provider Interface "Artifact Repository"; the term is Local Repository, matching the Go context `localrepo` and the dashboard page, and "artifact" stays the word for what it holds. Changed the same day: `ready` also requires every declared image to be stored, after a lab deployment timed out pulling an image whose one-time prefetch had stopped partway while the repository already read `ready`. Changed again the same day by the user's decision that each Site chooses whether its deployments use the Local Repository (`serveDeployments`, off by default) instead of every deployment requiring it; `ready` also requires the spec to serve deployments, and the playbook flag and trusted variable became `fetchesArtifacts` and `swallow_artifacts`. Changed 2026-11-11 by the user's decision that the choice is a Local Repository Mode (`upstream`, `cache`, `offline`) rather than a boolean, so a Site can use it as a cache without waiting for it to synchronize; `ready` follows the mode, and a source counts as served while a resync of it runs, so the daily resync no longer refuses deployments.
