# Platform

- Bounded context: Platform Management.
- Definition: A Kubernetes or Slurm runtime environment that Swallow deployed, including a single-node Kubernetes installation. Swallow owns its policy and lifecycle intent, deploys it, observes membership from the runtime's own API, and — for a deployed Kubernetes Platform — manages its in-cluster resources live through the same API.
- Allowed meaning: A Platform is a desired-state resource: it is created from a spec — its members with their roles, the type's settings, and how members get an operating system — and Swallow installs it once the creation's Change Plan is approved, producing a durable Workflow and a Swallow-owned credential. Later changes are written to the spec; destructive ones wait on a Change Plan, and the platform controller converges the rest and judges the Platform's Conditions. Deleting a Platform marks its spec absent; its approved uninstall removes the runtime from its targets and then the record. Deleting only the record removes the record and Swallow-owned projections without touching hosts. A Platform claims its members (Platform Claim) until its uninstall succeeds or its record is deleted, so a Platform's Servers are released only through its uninstall with release servers, never directly, and cannot be deleted while claimed. A deployed Kubernetes Platform additionally exposes a live cluster explorer (namespaces, applications, pods, apply, node cordon) that reads and writes the runtime's own API on demand and stores nothing.
- Disallowed meaning: Platform must not mean swallow itself (the system is named `swallow`), a Site, a provisioner Integration, an arbitrary Server group, a Kubernetes workload, a durable copy of the runtime internal state, or a single-software installation (a Docker CE, Podman, or NFS install is Managed Software, whose deploy target is one software rather than a multi-component runtime). Deleting only the record must not imply host-side uninstall. A Platform is not a registration of a runtime Swallow did not deploy: Swallow manages only self-deployed Platforms, and the public API no longer registers an existing one (the OS-provisioning import of an existing Server is unrelated and not a Platform).
- Synonyms: None.
- Deprecated terms: Cluster, when naming the Swallow aggregate or public resource; Forget, when deleting a Platform record; register/registered, when naming a public way to attach a runtime Swallow did not deploy (kept only as a one-release compatibility state for pre-existing records).
- Examples: A standalone k0s installation Swallow deployed is one Kubernetes Platform. A pre-existing `registered` record can still be deleted but never uninstalled and offers no cluster explorer. A failed uninstall retains the Platform for diagnosis and retry.
- Related terms: swallow, Server, Node Role, Kubernetes Topology, Kubernetes Application, Workflow, Platform Lifecycle State, Platform Claim, Integration, Exporter Ownership, Monitoring Link, Managed Software, Platform Module, Desired State.
- Change note: Renamed from Cluster on 2026-09-03 so the aggregate covers single-node and multi-node runtimes without implying a particular topology ([decision 014](../../../decisions/014-platform-resource-language.md)). Kubernetes cluster remains valid only when referring to the external technology itself. On 2026-09-05, `swallow` was added to Disallowed meaning so `Platform` never denotes the system itself ([decision 015](../../../decisions/015-platform-term-disambiguation.md)). On 2026-09-19, narrowed to self-deployed only and given a live Kubernetes cluster explorer; the public register-existing path was removed, leaving `registered` a one-release compatibility state ([decision 032](../../../decisions/032-self-deployed-platform-management.md)). On 2026-10-29, Uninstall gained an explicit choice to also delete the record after it succeeds; Delete stays record-only and Forget stays deprecated ([decision 010](../../../decisions/010-cluster-lifecycle-actions.md) amendment). The same day its deployment's hold on its Servers became a stored Platform Claim, which also refuses releasing those Servers directly ([decision 067](../../../decisions/067-platform-claim-on-server.md)). On 2026-10-30, each kind of Platform became provided by a Platform Module that defines its spec ([decision 070](../../../decisions/070-core-providers-and-extensions.md)), and the Platform's intent became its Desired State ([decision 069](../../../decisions/069-swallow-owns-desired-state.md)); the current lifecycle behavior above is unchanged until the Platform migrates. On 2026-11-01 a Platform became a spec/status resource: it is created from its spec, changed through it, and deleted by marking it absent, each destructive step behind a Change Plan ([decision 076](../../../decisions/076-change-plans.md)); deleting only the record remains for a Platform whose hosts are left as they are.
