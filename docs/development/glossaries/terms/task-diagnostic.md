# Task Diagnostic

- Bounded context: Automation (swallow-owned intent and execution).
- Definition: The structured, durable explanation of why a Task attempt failed, attached to the Task's normalized error and kept with the Task in swallow's store. It has two layers: the user layer says what happened, who is affected, and what to do next; the admin layer is the evidence behind it.
- Allowed meaning: The user layer is the error's message, the affected target (a Server or Platform among the Task's targets), and the remediation (the next step, in the user's terms). The admin layer is the Failure Class, the endpoint and the provider or platform operation that failed, the cause (the causal chain as text), the attempts, elapsed time, and budget of the wait that gave up, its last observation, and the events the provider recorded about the target. Every text in it is redacted, not erased: secrets are masked and the rest of the cause is kept. A Task Diagnostic belongs to one attempt; the Task keeps only its latest, and the Task's timeline keeps each earlier attempt's code, message, and Failure Class. A Task's wait observation — what a running Task waits for, published while it waits, with its attempts, elapsed time, and budget — is not a Task Diagnostic: it describes a Task that has not failed, is advisory, and is cleared when the attempt ends; when a wait gives up, its last observation and numbers move into the Task Diagnostic.
- Disallowed meaning: Not the error code, which is the only part a client or policy branches on (with retryability); not raw Runner output, logs, or a provider dump; not a place for secret values; not a second outcome — the Task's status and error remain authoritative. Not used to decide whether a Task may be retried.
- Synonyms: Diagnostic (inside the Automation context).
- Deprecated terms: None.
- Examples: "The `provision-os` Task failed with `deployment_stalled`; its Task Diagnostic names Server srv-1 as affected, says to open the Server console before retrying, and shows a transient Failure Class, the provisioner endpoint, twelve observations over the 30-minute budget, and the provider's last events." "While `wait-for-ssh` runs, its wait observation reads 'srv-1 refuses SSH connections'; it is not a Task Diagnostic until the wait gives up."
- Related terms: Task (carries it in its normalized error), Failure Class (classifies it), Runner (builds it), Workflow (its timeline keeps earlier attempts' failures).
- Change note: Added 2026-11-05 ([decision 077](../../../decisions/077-task-diagnostics-and-wait-policy.md) (Task diagnostics and wait policy)): a Task's failure had only a code and a fixed sentence, which neither told the user what to do nor kept the evidence an administrator needs.
